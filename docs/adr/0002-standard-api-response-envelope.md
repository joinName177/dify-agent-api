# ADR 0002：统一 API 响应信封

## 状态

已接受，前后端协调切换。

## 背景

原有 API 只为错误响应提供字符串业务 `code / message / requestId`，成功响应直接返回资源，登出使用无响应体的 `204`。客户端因此无法用统一方式校验、关联和处理成功结果，也混淆了 HTTP 状态与业务失败原因。

当前服务尚未发布需要长期兼容的旧客户端；SPA 与 API 在同一变更中更新锁定的 OpenAPI artifact、SHA-256、生成代码、测试和运行时配置，因此不保留双响应结构或兼容分支。

## 决策

保留 HTTP 方法和状态码语义，并统一 JSON 信封：

- 成功：`code / message / requestId / data`
- 失败：`code / errorCode / message / requestId / errors?`

成功和失败的数字 `code` 必须等于实际 HTTP 状态码。失败响应的 `errorCode` 是稳定的大写业务机器码；客户端只根据已知 `errorCode` 映射本地化提示，不直接向用户展示远端 `message`。具体资源只放在 `data`；字段校验问题只放在错误响应的 `errors`。

注册继续返回 HTTP `201` 且响应体 `code` 为 `201`，认证、读取和登出返回 `200`；认证失败、冲突、非法输入、限流和服务故障继续使用对应的 `4xx/5xx`，响应体 `code` 与之相同。登出从 `204` 改为 `200`，以返回标准信封。

未知路由、错误 HTTP 方法和中间件拒绝也使用标准错误信封。OpenAPI 是唯一传输契约，Go 与 TypeScript 类型只能由该契约生成。

## 备选方案

- 只提供 HTTP 状态码而不提供 `errorCode`：无法区分共享同一状态码的业务失败原因。
- 所有响应返回 HTTP `200`：会破坏缓存、代理、监控和通用客户端对 HTTP 错误的判断，拒绝采用。
- 同时支持旧结构和新信封：当前没有已发布兼容对象，会形成双契约和迁移债务，拒绝采用。
- 前端引入 Axios：现有 `fetch` 已覆盖取消、超时、Cookie、Header、JSON 和 Schema 校验，引入第二网络栈没有收益。

## 后果

SPA 和 API 必须协调发布，旧成功响应结构不再受支持。发布时必须同步 OpenAPI artifact、digest、前端生成物及 Runtime Config。契约测试必须同时覆盖成功信封、错误信封、未知业务码、畸形响应和 HTTP 负向路径。
